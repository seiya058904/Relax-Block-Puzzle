## 结论

确认两个真实问题：一项 P1（旧管理员验证与撤销组合可污染正式最高分）和一项 P2（暂停消耗连击窗口）。未发现可证实的 Board/Piece 边界、同时清线、三件套规则或生成预算错误；因此不建议更改它们的规则、分布或搜索预算。

### CORE-01 / P1 — 已取消管理员验证在新局完成，撤销恢复正式计分资格

- **实际平台路径**：WeChat。Web/Android `useUndoTool` 含有相同的资格恢复代码，但它们正常 UI 中管理员启用是同步的，没有这条异步验证完成路径；不把其潜在代码缺口误报为已复现平台缺陷。
- **基线位置**：微信 `js/game/GameState.js:1476`（`submitAdminCode`）、`:552`（关闭面板不失效请求）、`:1496`（旧成功结果关闭面板）、`:1537`（启用管理员使资格失效）、`:1108`（撤销无条件恢复快照资格）；Web/Android 同构撤销为 `:1076`。共享 `shared/js/game/ScoreManager.js:44–47` 只检查 `bestScoreEligible`。
- **影响**：满足受信任管理员验证的玩家，在异步验证尚未完成时取消并开普通局，仍会被旧响应切入管理员模式；撤销旧普通局快照后，可用管理员模式下的放置更新正式最高分。没有绕过服务器身份验证；这是成功验证结果的生命周期和正式成绩隔离缺陷。
- **复现**：`node --disable-warning=MODULE_TYPELESS_PACKAGE_JSON audit/core/admin-undo-repro.mjs`（相对路径按工程部署位置调整）。脚本通过现有 `loadVersion` 加载真实微信模块，使用真实生成方块和 `startDrag → moveDrag → endDrag`，只以受控 Promise 代替延迟的服务器成功回复。
- **步骤**：主页打开管理员面板、提交 → 请求未完成时取消 → 开普通局 → 合法放置，生成 `bestScoreEligible=true` 的撤销快照 → 完成旧验证，当前资格变为 `false` → 使用撤销，资格被重新写成 `true` → 再放两块。
- **基线证据**：`admin-undo-baseline.log`；`adminModeAfterUndo=true`、`eligibilityAfterUndo=true`，正式最高分从 `10` 增长为 `20`，产品不变量断言退出码 `1`。
- **根因**：请求未绑定面板/局的生命周期；失效资格错误地被当作完全可逆的普通快照字段；计分器没有管理员模式的额外防线。
- **最小修复建议**：微信验证使用递增 token；关闭面板、重置主页/新局使旧 token 失效。每次提交采用新 token，旧完成/旧失败不再修改认证状态、弹层、提示或错误。有效请求仍保留正常成功/失败及隐藏后恢复的行为，不更改后端校验或权限来源。三端撤销使用单向资格：当前资格、快照资格均为真且未处于管理员模式才可恢复为真。共享 ScoreManager 可加管理员隔离防线。
- **必要反证**：正常有效成功仍启用；有效 false/reject 留面板并显示原错误；旧成功、旧失败、重开、重新开面板和重复提交均不能覆盖最新状态；后台隐藏本身不取消仍有效的验证（现有回归明确支持隐藏期结果）。启用后再关闭管理员的本局也不能因撤销获得资格。
- **置信度**：高。基线执行失败且父代理安排并发审计代理独立确认。

### CORE-02 / P2 — 三端暂停/设置期间连击窗口继续消耗

- **平台**：WeChat、Web、Android，分别执行复现。
- **基线位置**：微信 `js/game/GameState.js:932–949`，Web/Android `:900–917`；`handleLineClear` 使用 `Date.now()` 计算清线间隔。`canAdvanceTime()` 虽冻结帧倒计时，但不抵消墙钟消耗。
- **规范依据**：`docs/UNIFIED_SPEC.md:133` 明确“游戏暂停时冻结组合窗口”，`:300` 再次要求“暂停冻结，超时归零”；3 秒窗口及计分公式均应保留。
- **影响**：在两次清线之间打开暂停或设置后，即使有效游戏时间不足 3 秒，再次清线仍被误判超时，连击计数、提示/音效回到单次清除。该问题不改变当前分数公式。
- **复现**：`combo-pause-repro.mjs`。`t=1000` 首次清线，`t=1500` 暂停或设置，`t=11500` 恢复，`t=12000` 再次清线；有效经过时间 1000ms，暂停 10000ms。
- **基线证据**：`combo-pause-baseline.log`；三个平台 × 两类弹层的 6 项都得到 `actualComboCount=1`，期望 `2`；退出码 `1`。另有“无暂停、没有帧、墙钟经过 4000ms”对照，正确要求连击过期，防止错误改为 idle 停走的动画时钟。
- **最小完整修复方案**：使用扣除暂停区间的逻辑墙钟。GameState 维护运行时 `pausedAt:null`、`excludedMs:0` 及宿主隐藏标记。`getComboNow() = (pausedAt ?? Date.now()) - excludedMs`。第一次从运行变暂停时记时间，最后一个暂停原因解除后只累计一次暂停时长。`handleLineClear` 改用逻辑墙钟；快照中的 `lastClearTime` 保留此时钟值，但不回滚计时器自身的累计偏移。首页/新局同时重置 combo 与时钟。不得直接使用 `feedback.clock`，其在前台无帧时停止。
- **完整接入点**：`setScreen`；`open/closeSettings`；`open/closePause`；`open/closeAdminPanel`；`open/closeRevivePrompt`；`initializeHomeState` 直接设置首页的路径；三端 Main 的 `handleAppBackground/Foreground`。`reset/useUndoTool/triggerGameOver` 最终走 `setScreen`。会员面板、清分确认、返回首页确认都在现有父弹层之内，不产生独立暂停原因。
- **必要反证**：暂停/设置、后台、后台与弹层交叠、重复 hide/show、先关弹层但仍后台不能恢复时钟、先前台但弹层仍开不能恢复时钟、idle 4 秒仍过期、撤销不重复扣除暂停、新局/复活后没有旧连击。
- **置信度**：高。明确冻结规范与六项基线执行失败。

## 已排除或仅列为待验证的疑点

1. **Board.canPlace 对 NaN/空 cells、Board.place 不自行复验**：固定库中的格子均为有限非负整数且非空；真实 GameState 放置会调用 `canPlace`；现有输入从已验证布局产生锚点。未建立玩家可达的非数值/空块路径。仅以直接调用低层 API 的畸形参数不能证明产品缺陷，不建议为此改核心规则。
2. **行列同时清除导致双计格子**：`clearLines` 使用行列集合的并集；独立 oracle 的 5715 条清线及跨端回放未出现棋盘或分数偏差。计分按“行数 + 列数”，交叉格仅在棋盘清除一次是有意规则。
3. **待清线时撤销**：`canUseTool` 同时阻止 pendingClear/inputLocked，真实输入入口也阻止此时操作；已验证锁解除后撤销恢复。不能绕过 guard 手动调用来宣称竞态。
4. **不可能完成三块时生成器返回失败/退路**：严格尝试加末尾 relaxed attempts 是现有保守设计，只要求至少一个即时合法放置；“不是三块都能放”本身不是缺陷。不可将其修成保送三块或无限搜索。
5. **生成可能返回少于 3 块**：静态观察到通用 validator 没显式检查长度，但现有固定池/家庭上限下 `createCandidateRack` 的 fallback 总能为三槽提供家族，未建立真实不完整候选路径。长局生成和主代理现有 simulation 继续作为证据；不为畸形外部 options 改行为。
6. **master validator 接受三个同 base**：既有测试明确把 validator 的宽松性与实际候选生成的 soft/hard 策略区分；不能仅据 validator 接受手造三同块即改平衡。真实候选池仍按其配置筛选。
7. **`evaluateRackViability` 搜索耗尽可能低估最优深度**：搜索有限预算是明确设计，false 不能被解释成数学上绝无三步解；实际生成末尾会退到即时合法移动。未发现错误 true、修改原棋盘或越界预算的真实证据，不改预算。
8. **无路可走但仍有道具时立即结束/复活**：现有冻结流程就是剩余块无合法移动后进入结束/复活；允许在结束弹层先用道具属于新规则，不能作为 Bug 修复擅自加入。
9. **极端整数溢出**：当前所有实际 cellCount/lineCount 均受 10×10/固定库约束；长局数值有限且精确。超过 `Number.MAX_SAFE_INTEGER` 的任意注入分数未建立正常游戏可达路径，不宣称已复现溢出。
10. **Web/Android cancelDrag 清空所有表现状态，WeChat 只清拖拽**：已转交 Input & Rendering Auditor 独立沿 touchcancel/生命周期路径验证，避免重复制定不完整修复。
